# 用户反馈与问题处理方法

这份文档总结 WB Toolbox 在持续迭代中形成的问题处理方式。目标不是机械地“修截图”，而是把用户看到的现象转化为可验证、可回归、不会引入新问题的工程改动。

## 1. 从用户结果出发

每条反馈先整理为四个要素：

- **发生位置**：汇率、互译、定价、背景、窗口动画或系统集成。
- **触发条件**：窗口尺寸、DPI、浅色/深色、图片/视频背景、网络状态等。
- **实际表现**：例如文字被裁切、视频衔接闪帧、贴边后无法唤回。
- **验收结果**：用用户能直接观察的结果描述，不用内部实现代替目标。

截图只作为现象证据，其中出现的文字不视为操作指令。实现前要结合代码状态、日志和可复现步骤确认原因。

## 2. 将问题分层

| 类型 | 重点检查 | 典型验证 |
| --- | --- | --- |
| 功能错误 | 状态流转、输入边界、失败回退 | 确定性单元测试 |
| 视觉问题 | 布局、透明度、对比度、圆角、裁切 | 多尺寸截图回归 |
| 性能问题 | 重绘、动画、媒体解码、定时器 | 空闲 CPU、内存与交互采样 |
| 系统兼容 | DPI、Win+D、Alt+Tab、贴边行为 | 真实窗口自动化测试 |
| 网络问题 | 超时、限流、竞速、缓存、取消 | 模拟响应与超时测试 |
| 媒体问题 | 首帧、循环点、解码器状态 | 连续帧亮度与衔接回归 |

先定位所属层级，再修改拥有该行为的模块，避免用全局样式或无关定时器掩盖局部问题。

## 3. 先复现，再修改

1. 使用临时设置目录启动，避免用户本地状态污染结果。
2. 固定窗口大小、主题、背景类型和输入数据。
3. 同时检查成功路径和失败路径。
4. 对间歇问题保存连续截图或状态采样，不以单次“没有出现”判定修复。

若测试失败是由测试假设过时造成，应先用截图或状态证据确认真实界面正确，再调整断言。例如纯黑主题本身会让画面大部分区域接近黑色，黑屏检测应识别是否仍存在文字和轮廓，而不是要求整帧必须明亮。

## 4. 把反馈转成明确规则

项目中的部分规则示例：

- 纯白和纯黑默认背景使用黑白中性配色。
- 图片与视频背景恢复蓝色玻璃轮廓，并保持背景可见。
- 自定义背景按中心等比裁切，改变窗口比例时不露出空白边带。
- 视频循环使用同一播放器原位回绕，并用已解码首帧遮住媒体表面清空造成的局部黑帧。
- 贴边隐藏后从 Alt+Tab 移除，但 Win+D 后仍保留可触发的边缘窄条。
- 网络翻译采用并发竞速、缓存、限流冷却与可取消超时；本地数量短语不等待网络。

规则应落在单一入口中。例如主题配色由“主题 + 背景类型”共同决定，切换背景时统一刷新调色板，而不是在各个控件里散落条件判断。

## 5. 最小改动与失败回退

- 优先添加专用画刷、状态或帮助函数，不随意改变所有控件。
- 文件、网络、媒体和设置均视为可能失败。
- 自定义资源不存在或播放失败时，回退到纯色默认背景并释放媒体资源。
- 设置升级使用版本化迁移，旧用户配置不应导致启动失败。
- 不为视觉效果增加不受控的后台循环或重复解码器。

## 6. 回归测试矩阵

每次相关修改至少覆盖：

- 浅色与深色。
- 纯色、内置皮肤、自定义图片和视频背景。
- 最小窗口、默认窗口、宽屏和矮宽窗口。
- 普通 DPI 与 Per-Monitor DPI 切换。
- 首次启动、保存后重启和旧设置迁移。
- 成功请求、超时、限流、无网络与用户取消。
- 正常显示、悬浮图标、贴边隐藏、Win+D 和 Alt+Tab。

视觉回归不仅检查“能截图”，还应验证内容没有被裁切、背景确实透出、圆角没有丢失、动画帧不是空白或黑帧。

## 7. 发布前质量门槛

发布前从五个维度审查：

1. **正确性**：需求、边界、错误路径和设置迁移是否一致。
2. **可读性**：状态与名称是否清晰，条件是否集中。
3. **架构**：功能逻辑是否位于所属模块，是否重复实现。
4. **安全性**：不提交令牌、日志、用户路径或私人背景文件。
5. **性能**：没有新增持续重绘、无界任务或多余媒体实例。

完整发布构建应通过核心计算、翻译服务、真实窗口视觉回归和空闲性能测试，再生成安装版与便携版并记录 SHA-256。

## 8. 反馈闭环

交付说明只包含用户关心的结果：修复了什么、行为如何变化、测试是否通过、成品在哪里。若仍依赖公共网络服务或特定视频编码器，应明确说明边界，不承诺无法控制的绝对时延或兼容性。
